# 起票分析（需求 → 拆票落盘）

**用法**：把本文件拉进对话 → 在下方「本次待分析内容」粘贴您想修改的杂散描述（可多条、可不结构化）→ 发送。
**约定**：AI 只负责**分析归类并把票落盘**到 `docs/工程/票/`，**不直接改代码**；票库规则见 [`docs/工程/票/README.md`](../../docs/工程/票/README.md)。本文件不承载具体票内容，每次使用改写下方填写区即可。

---

## AI 执行流程（不用改）

收到「本次待分析内容」后，按序执行：

1. **读输入与票库现状**
   - 读 `docs/工程/票/README.md`（类型 / 状态机 / 编号规则）与各分区台账，确定各区**当前续号**（Bug2、S2、T1、F1 起沿现状，查台账不得臆断）
   - 把输入**逐条归类**：Bug 票（已确认的错误行为）／ 式样变更票（已确认要改的式样或需求变化）／ 调查票（问题不明需先查清）／ 功能体验票（新功能或体验增强）
2. **文档优先分析**（先不动代码）
   - 按 `docs/README.md` 分类定位相关文档：式样说明书、**`docs/画面/`**、架构 / 路由设计、既有票（是否已有同题 / 相关票，重复则只指不建）
   - 依据文档判断每条的类型、现状、影响范围、是否含「待定」或规格不清
   - **关联画面预估**：对照诉求与画面目录 / 路由表，在拟建票「关联画面 · 预估」列出可能波及的 `docs/画面/…` 路径（不确定标「待确认」）；「实际改动」留空
3. **文档不足 → 定点读码兜底**
   - 仅当文档无法判断现状 / 影响时读代码，且只读被定位的 `android/app/src/` 相关文件，禁止无目的通读
4. **归类产出（不擅自假设）**
   - 能明确归类的 → 拟票
   - 属「待定」或规格不清的 → 优先开调查票（T）；或列出问题等用户确认，**不开实施票**
   - 无法归类的输入 → 逐条回列疑问请用户补充，不硬建
5. **落盘**
   - 按分区续号 → 复制 `docs/工程/票/_模板/` 对应模板 → 新建 `docs/工程/票/<分区>/<票号>-简述/README.md` 并填写（删除模板顶部说明行；含关联画面预估）
   - 在分区 `README.md` 台账表追加一行（票号 / 标题 / ☐ / 目录链接）
   - 票间有关联的，在「关联」栏互记
6. **回执**
   - 汇总已建票清单（票号 / 类型 / 标题 / 目录 / 状态 ☐ / **预估关联画面**）
   - 注明与既有票重复或相近的内容（只指不建）

**硬性约束**

- 一票一条主题，不把多条需求杂糅进一张票
- 票号与类型只进不退，遵循 `docs/工程/票/_模板/README.md` 约定
- 只建票与登记台账；**不写代码、不改文档正文**
- commit 纪律按 `shared/rules/git-convention.md`，开发流程按 `shared/rules/dev-convention.md`
