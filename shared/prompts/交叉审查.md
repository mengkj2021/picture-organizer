# 交叉审查（双 AI 互审）

**用法**：把本文件拉进对话 → 在下方「本次审查」填票号与审查对象 → 发送。  
**约定**：由**未写该票实现**的一侧审查（CodeBuddy 写 → Cursor 审，或反向）。本提示词为**可选工具**，不纳入 `功能开发.md` 强制流程；审出问题回原票改（或另起 Bug/式样票），勿在本会话直接大改实现除非用户明确要求。

**目的**：写与审换脑，抓自审易漏的多余抽象、包结构不符、边界缺口、验收跑偏、改动漂移。

---

## AI 执行流程（不用改）

收到「本次审查」后，按序执行：

1. **锁定审查对象**
   - 读填写区：票号、审查对象（diff / 文件列表 / 提交说明）、实现方与审查方
   - 读 `docs/工程/票/<分区>/<票号>-简述/README.md`：诉求、方案、**验收标准**（逐条对照）
   - 若票不存在或对象为空：停下请用户补全，不要猜
2. **定点读改动**
   - 只读审查对象列出的文件及票开发记录 / 当日开发日志中点名的路径
   - 需要对照时再读相邻约定（如 `shared/rules/dev-convention.md` 包结构指向的架构 §2、相关画面 README）
   - 禁止无目的扫全库；禁止借审查之名重写实现
3. **按固定清单审查**（每条必须给结论）

   | # | 审查项 | 关注点 |
   |---|---|---|
   | ① | 多余抽象 / 造轮子 | 是否引入不必要的层、工具类、重复已有 util/Repository 能力 |
   | ② | 包结构与现有模式 | 是否符合架构 §2 与同包既有写法；规则/文档同步是否漏处 |
   | ③ | 边界与错误分支 | 空值、失败路径、权限/IO、用户取消、平台差异是否处理 |
   | ④ | 对照验收标准 | 做的是否就是票上要的事；有无漏项或「做了别的事」 |
   | ⑤ | 改动漂移 | 是否改了票范围外的文件/行为；有无顺手重构、无关格式大扫 |

4. **输出格式**（必须按此结构；全部「通过」才可写「审查通过」）

   ```
   ## 交叉审查结果（票号）

   - 实现方：…
   - 审查方：…
   - 审查对象：…

   | # | 审查项 | 结论 | 说明（问题须含文件位置 + 建议） |
   |---|---|---|---|
   | ① | 多余抽象 / 造轮子 | 通过 / 问题 | … |
   | ② | 包结构与现有模式 | 通过 / 问题 | … |
   | ③ | 边界与错误分支 | 通过 / 问题 | … |
   | ④ | 对照验收标准 | 通过 / 问题 | … |
   | ⑤ | 改动漂移 | 通过 / 问题 | … |

   ### 总评
   - 审查通过｜有问题待改（列优先修复顺序）
   - 建议回写：原票开发记录 / 或起 Bug 票（若属既有缺陷）
   ```

5. **收尾约束**
   - 默认**只输出审查结果**，不直接改业务代码
   - 若用户填写区写明 `审完可改`：仅修清单标为「问题」的项，改完后在同回复补一版「复审」表
   - 不更新票状态为 ✅（那是实现方收尾职责）；可将本结果粘贴进票开发记录或开发日志

**硬性约束**

- 不做 CI、不改 `功能开发.md` 强制步骤（除非另有票）
- 审查结论必须可定位（文件路径；必要时行号或符号名）
- 无充分依据不标「问题」；不确定标「待确认」并写出缺什么信息
