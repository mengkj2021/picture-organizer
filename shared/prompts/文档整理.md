# 文档整理

**用法**：把本文件拉进对话 → 填写下方「本次整理」→ 发送。  
**用途**：某功能已落地后，对照**当前代码真相**，把全项目相关文档一次对齐；**默认只改文档，不改业务代码**（除非填写区写明要顺带修文档笔误对应的极小标注，仍不改逻辑）。

**约定**：式样书中「待定」项不得擅自写成已确认；过时「尚未实现 / ☐」若代码已有，应改为已实现 / ✅ 并写清依据。

---

## AI 执行流程（不用改）

收到「本次整理」后，按序执行：

1. **锁定范围**
   - 以填写区中的功能名 / 画面 / route / 改动清单编号为准
   - 未写范围时：根据最近实现痕迹（新画面文档、Routes、改动清单状态）推断，并在方案里写明推断范围，等用户确认后再改
2. **定点读码（真相源）**
   - 只读与本功能相关的：`navigation/Routes.kt`、对应 `ui/<screen>/`、涉及的 `data/` / `util/`、`android/gradle/libs.versions.toml`（若有依赖）
   - 禁止无目的扫全库
3. **文档对照清单**（按相关性勾选；无变动则跳过，并在结果中注明「无需改」）

   | 文档 | 检查点 |
   |---|---|
   | `docs/画面/<画面>/README.md` | 总览功能清单、进出、数据依赖、§10；区域索引表是否齐全 |
   | `docs/画面/<画面>/` 相关区域文件 | 如主画面 `待处理一览/菜单.md`、`一览.md`；详情 `标签.md` 等与代码一致 |
   | `docs/设计/路由设计.md` | 第 3 节登记；文档列指向各 `README.md`；开发记录 |
   | `docs/式样/项目式样说明书.md` | §3.1 依赖版本；§4 功能状态；§5 画面表；§8 开发记录 |
   | `docs/设计/架构设计.md` | 包结构、数据流、Repository/工具类、后续迭代、开发记录 |
   | `docs/工程/改动清单.md` | 对应 C/B 项状态；建议顺序；去掉已完成项的过时描述 |
   | 相关其它画面目录 | 交叉入口（如主画面「可前往」）是否已写 |
   | `docs/日志/开发日志-YYYY-MM-DD.md` | 若填写区要求写日志：新建或补当日条目（勿虚构未做事项） |
   | `docs/README.md` / `docs/画面/README.md` | 分类与画面索引是否需更新 |
   | 根 `README.md` / `shared/README.md` | 仅当能力概述或 prompts 列表过时时更新 |

4. **方案与修改**
   - 默认：先列出「拟改文档 + 将改什么（要点）」与「发现的过时/矛盾处」，等用户确认后再改文件
   - 若填写区写明 `直接整理`：跳过确认，直接改文档
5. **原则**
   - 文档服从代码；代码未实现的保持「尚未实现」或 ☐，不要提前勾完成
   - 删除或改写与现状矛盾的句子，避免同一事实在多处说法不一致
   - 不扩写无关章节；不把「待定」改成已定
   - 整理结束后清空本文件「本次整理」填写区（恢复为空代码块）
6. **本模板默认不实现新功能、不重构代码**；若发现文档与代码严重不符且需改代码才能对齐，只列出问题，请用户改用 `功能开发.md`

**填写示例**（勿留在下方代码块里）：

```
范围：图片详细画面 / C1+C2 / image-detail
直接整理
补充开发日志：是
```
