## 用户诉求 / 场景

- 要解决的问题或场景：阶段一复盘实证——文档版本（v0.9）、App 版本（0.0.1 / 曾 0.1.0）、versionCode（1）三套号互不参照、无统一出处；发版语义待定（项目计划 §5）。公开日临近，三套口径若不自洽会露怯，且后续每次发版缺"谁增谁不变"的权威依据。
- 预期效果：式样书建立版本矩阵表（文档号 ↔ 产品 milestone ↔ versionName ↔ versionCode 语义），发版时按语义递增 versionCode / 演进 versionName；文档修订与代码改版各自有出处可查。
- 是否已有式样依据：阶段一复盘 §3.5（已列候选调查/变更）。

## 需求确认（接票前若为「待定」先在此澄清）

- 范围：建矩阵与语义规则（哪档动哪、何时 +1）入式样书 §3.1；与项目计划 §5「版本 0.1.0 首个公开 tag」对齐拍板；落地时把 `versionName` 调整到拍板值。
- 不改动：不引入自动化版本脚本（语义规则文档化即可，够用）。
- 引用基础：App 版本号权威处 = `android/app/build.gradle.kts`；文档号权威处 = 式样书自身标题行——矩阵表给出对照与演进规则，代码/文档各自改各自出处，矩阵只做登记不反客为主。
