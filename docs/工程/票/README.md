# 票库 · 起票制开发（docs/工程/票/）

> 开发模式：**起票制**——任何改动先起票、再接票实施。仓库根 `README.md`、[`docs/README.md`](../../README.md)、[`shared/rules/dev-convention.md`](../../../shared/rules/dev-convention.md) 均引用本目录。
>
> 本目录只维护「票」。全量票一览（已完成 + 待办 + 建议顺序）见本目录 [`改动清单.md`](改动清单.md)；更早的功能号历史（A1–A8、C1–C10、B3/B5/B6、D1、P1–P6 等）见其「历史功能号」节与 [docs/日志/](../../日志/) 开发日志。

## 1. 为什么起票

以编号票替代「直接说要求」，让每次改动都有：类型、编号、状态、出处（现象 / 需求）、验收标准与开发记录，全程可追溯。未确认项在票内澄清后再实施，不擅自假设。

## 2. 票类型

| 前缀 | 类型 | 用途（历史对应） | 分区目录 | 序号起点 |
|---|---|---|---|---|
| `BugN` | Bug 票 | 已确认的错误行为（原改动清单 Bug 分区） | [`bug/`](bug/) | **Bug2**（Bug1 已归档，[补建目录](bug/Bug1-教程画面系统栏裁切/)） |
| `SN` | 式样变更票 | 已确认要改的式样 / 需求变化（原 S 分区） | [`式样变更/`](式样变更/) | **S2**（S1 已归档，[补建目录](式样变更/S1-状态不算标签/)） |
| `TN` | 调查票 | 问题不明，先调查确认再定方案（原「待定」调研） | [`调查/`](调查/) | T1 |
| `FN` | 功能 / 体验票 | 新功能（原 C 类）或体验增强（原 P 类） | [`功能体验/`](功能体验/) | F1 |

## 3. 一票一目录与命名

- 每票在所属分区下建**独立目录**，票主体为目录内 `README.md`：
  ```
  docs/工程/票/bug/Bug2-简短标题/README.md
  ```
- 目录命名：`票号-简短标题`（连字符分隔，标题 3–10 字概括，避免超长）。
- 模板位于 [`_模板/`](_模板/)，起票操作见 [`_模板/README.md`](_模板/README.md)。

## 4. 状态机

```
☐ 待实施 → 🚧 进行中 → ✅ 已完成
                ↘ ❌ 不采纳（驳回 / 不值得做）
```

- 调查票结论「不值得做」→ ❌；结论「值得做」→ 转成对应类型的新票（原调查票标 ✅，注明转票号）。
- 状态符号沿用改动清单历史约定，各分区台账与票内均用同一符号。
- **完结不删**：票验收（✅ / ❌）后目录与台账行一律保留，只流转状态，并在票内补「完结复盘」（模板已内置）。
- 有价值的教训在验收后登记 [错题本](../错题本.md)，票内注明登记与否。

## 5. 生命周期

| 阶段 | 责任 | 动作 |
|---|---|---|
| 1. 起票 | 用户 | 复制 `_模板/` 对应模板 → 分区下建 `票号-简述/` → 填票 → 登记分区台账表 |
| 2. 排期 / 接票 | 对话（AI） | 拉入 `shared/prompts/功能开发.md` 按票执行；涉及式样「待定」先回票澄清 |
| 3. 实施 | AI | 文档先行（涉及画面先画面文档）→ 代码 → 写开发日志（文件名带票号） |
| 4. 验收 | 用户 | Review diff → 票状态改 ✅ / ❌（不删票）→ 补「完结复盘」、登记错题本 → 决定 commit / push |
| 5. 归档 | AI | 已完成票同步进本目录 [改动清单](改动清单.md) 总台账 |

## 6. 与改动清单（总台账）的关系

- **改动清单**（[`改动清单.md`](改动清单.md)，本目录内）= 票库**总台账**：已完成归档 + 待办一览 + 建议实施顺序。分区台账管「票详情」，改动清单管「全景与排期」，两者配套维护。
- **进行中 / 已完成**票都在各分区台账维护；票验收后由开发对话同步改动清单总台账。
- **错题本**（[`docs/工程/错题本.md`](../错题本.md)）= 完结票教训的跨票汇聚（日期 / 出处 / 教训 / 规避），起票 / 接票前可先查同名教训。
