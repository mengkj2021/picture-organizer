## 要调查的问题

- 问题描述：在图片详细画面加一个「连接 AI」入口，把当前图片交给 AI，自动产出候选标签——技术路线是否现实、与项目定位是否兼容、成本几何。
- 为什么需要查清（若不查清的后果）：本项目当前定位「**全程本地运行、不联网**」（[AndroidManifest.xml](../../../../android/app/src/main/AndroidManifest.xml) 注释明示不声明网络权限；根 README 简介亦强调本地）；加 AI 若隐含联网 / 上云 / 引入 key，会直接触碰产品定位与隐私承诺，属方向性决策，必须先调查再定，不能凭印象直接起功能票。

## 已知线索

- 涉及画面 / 代码 / 文档 / 数据：
  - 画面：[图片详细画面 · 标签](../../../画面/图片详细画面/标签.md)、标签管理（候选标签 / 自动入库 S2）
  - 现状约束（写实）：
    1. **无网络权限、无网络库**：Manifest 未声明 `INTERNET`；技术栈（[式样书 §技术栈](../../../式样/项目式样说明书.md)）无网络 / HTTP 依赖；
    2. 图片存 **App 私有目录** `filesDir/images/{pending,confirmed,no_modify}`，用户以「本地整理私人照片」为使用场景；
    3. 标签体系已成型：图片 `tagsJson` + 全局词表 `tags`（S2 自动入库）——AI 产出的标签若要落地，应复走现有入口（选词 / 入库语义已定，不能绕开）；
    4. App 无任何账号 / 后端，唯一网络设施是「打包导出到本机 / FileProvider 分享」类本地能力。
- 已排除的可能：非「AI 生图 / 滤镜」类，用户指的就是**看图出标签**。
- 猜测与分歧点：
  - 云端多模态 API：效果最好，但需 `INTERNET` + 网络库 + **API key 管理与费用** + **图片上传第三方**——与「本地私人相册」定位冲突面大；
  - on-device 方案（本地视觉模型 / ML Kit 图像标注）：无网络但模型体积、标签语言（中文）、精度、维护成本待查；
  - 「折中形态」：功能做成**显式可选、默认关**的实验项，或仅对用户勾选/分享出去的图片生效——但仍绕不开上述基础问题；
  - 另需拍板：谁出 key / 费用、失败降级行为、是否只读不写（AI 只建议、用户确认才打标签）等。
