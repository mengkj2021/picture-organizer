## 要调查的问题

目标：把本仓库从「个人开发库」整理为**可对外公开 / 可复用的项目**。分四个子项调查：

1. **AI 开发模板化（可迁移复用）**
   - 现状：AI 双工具协作约定散在 `shared/`（README / rules / prompts / skills）与 `docs/` 各类文档中，与 picture-organizer 业务文档深度耦合，直接拿给其它项目难以复用。
   - 调查：哪些是**通用资产**（AI 开发介绍、dev-convention、git-convention、票驱动起票制、画面文档 SOP、prompt 模板），哪些是**本项目专属**；如何抽出一个「AI 开发模板包」（如 `shared/template/` 或独立文档），让新项目克隆后**最小裁剪**即可用（放哪、怎么引用、版本同步策略）。

2. **项目瘦身与文档精简**
   - 现状：`docs/` 约 118 个 md；`docs/日志/` 19 个文件（大量过程性流水账）；票库 20+ 张票（含 ☐ / 🚧 / ✅ 各态）。
   - 调查：哪些文档公开后**无价值甚至负面**（过程日志、废弃票、复盘里贬损性 / 内部吐槽内容）；公开版是否需要「精简树」（保留式样书 / 设计 / 画面 / 票库骨架，归档过程日志）；开发日志如何归并成精炼的「变更历史」而非逐日流水。

3. **隐私信息排查**
   - 现状：仓库内明确含个人标识（README 的账号 mengkj2021、邮箱 mengkj2021@163.com、SSH host 别名与 key 路径、机器路径示例），commit 历史同样含这些信息（含 git 身份 `mengkj2021 <mengkj2021@163.com>`）。
   - 调查：除账号外还有哪些隐私面（本机路径、`.ssh` 细节、Gradle 本地 zip 路径、任何真实文件路径 / 姓名）；排查手段（`git grep`、历史扫描工具）与脱敏策略（文档改写 vs 历史重写 vs 保留但模糊化）。

4. **公开时隐藏历史提交**
   - 调查：让新公开仓库「看不到之前的提交」的可选方案与各自代价——
     - a) 新仓库初始提交：只推「公开版快照」到全新空仓库（GitHub 换库 / 改名）；
     - b) 单提交 squash / 深度重写（`git filter-repo`、`--root` squash、孤儿分支）；c) 原库保留私有，公开库走镜像 / 迁移；d) 平台级「make repo public」直接公开原库（最省事但历史全见）。
   - 每方案查清：历史是否可被复原（reflog / PR / fork）、本地与远端操作顺序、是否影响已 clone 的副本、commit 作者信息能否一并清除。
   - **与目标的权衡（新增）**：本仓库 commit 带票号、是 AI 协作过程的可信证据；若「隐藏历史」与「展示 AI 协作」冲突，需评估中间态（如保留近期精化历史、仅清除作者邮箱/账号面、或新增「协作记录」目录说明历史归并原因）。

5. **开源观感工程（支撑「不错的项目」）**
   - 调查：目标仓库应具备的公共面资产现状与差距——README 观感（项目简介 / 截图 / 特性 / 快速开始）、开源 License（选型与文本落位）、CI（GitHub Actions：build + ktlint + 单元测试）、badge、Release 与 APK 下载说明、`android/` 能否被全新 clone 后直接构建（本地 Gradle zip 方案对外部用户不可行的替代做法）。
