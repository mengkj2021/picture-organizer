## 2. 成效（体制如何运作）

### 2.1 文档先行，代码后行
- 每画面先有 `docs/画面/<画面>/README.md`（10 节模板：概述 / 路由 / 功能 / 操作 / UI 壳层 / 返回 / 进出 / 数据依赖 / 待定 / 开发记录），再实现代码；新画面复制 `_模板/` 派生，一层目录 = 一个 route 画面（载体：`docs/画面/README.md`、dev-convention 强制约定 3）。
- 「新增画面流程」在 `docs/README.md` 固化为四步顺序；08-27 日志亦将「文档先行」写入计划。
- 画面 README §10 开发记录表随每个功能回写——文档不是一次性产物，而是逐日演进。

### 2.2 权威文档随代码演进
- 式样书版本矩阵（§3.1）每加依赖即时同步（coil / exif / datastore / exports + FileProvider）；Room v2→v3、路由表、架构包树与 `Routes.kt` 同步更新。
- 08-31-文档整理一次对齐式样 v0.9 / 架构 / 路由 / 全部画面 / 改动清单，并登记后续 backlog——是「阶段小结式整理」的样板。
- S1 一次变更同步 4 处文档（式样书 §4.3 / 架构 §3.3–4.2 / 主画面 README / 改动清单）。

### 2.3 编号分级与归档
- 改动清单按 A / C / B / P / D / Bug / S 分区编号，完成项移入「已完成」注记并注明见日志——backlog 可滚动不膨胀。
- 日志命名带编号后缀（`-C8`、`-B3-B5-B6`、`-D1`…），commit 信息带功能号，历史可 grep 定位。

### 2.4 每任务一篇日志 + 提交纪律
- 同日多项拆多篇日志；`提交注意事项.md` 固化中文提交纪律：UTF-8 无 BOM、`-F 提交说明.txt`（实测 PowerShell GBK 直传中文会**不可逆乱码**）、禁 `--force` / `git add .`、push 前自检（载体：提交注意事项.md，非日志正文）。
- 用户 Review diff、决定 commit / push 的边界贯穿全程（载体：dev-convention / 票库生命周期）。

### 2.5 双工具规则三处同步
- `shared/rules/` 为唯一源 → 复制 `.codebuddy/rules/` 与 `.cursor/rules/`；统一 frontmatter 免转换；改规则须三处同改（载体：sync-convention.md）。

### 2.6 未确认项边界
- 式样「待定」不得擅自实现（dev-convention 强制约定 1）；需求型改动默认「先方案后实现」，写明才直接改（prompts 功能开发）。

## 3. 缺陷与返工（含根因）

### 3.1 Bug1：高版本适配要求未前置进文档
- 成因（09-02-Bug1 自述）：`enableEdgeToEdge()` 后普通画面靠 M3 Scaffold 自动消费系统栏 inset，唯独 TutorialScreen 是裸 `Column` + 固定 16dp padding → 高版本系统栏裁切。
- 根因：**「edge-to-edge / inset 适配」这一普遍约束从未进入式样书或画面文档的统一规格**，`_模板` 派生画面时未把壳层约束带出。属文档覆盖缺位导致的高版本适配遗漏。

### 3.2 S1：状态标签概念混入标签体系的返工
- 直接文本证据（09-02-S1 自述）：「与式样书旧条款『确认完成也是一个标签』冲突」——**早期式样条款把状态当标签**，代码据此把状态词注入 tagsJson / Exif / 各写端。
- 反噬面：`tagsForStatus` / `withStatus` 等注入散落写端，读端靠 `userTagsOf` 过滤仍有漏点与脏数据（列表 chip 出现状态词）。S1 一次收口：7 个代码文件 + 启动迁移幂等清洗 + 4 处文档 + Mock 同步，为本阶段改动面最大的一项。
- 教训：**概念模型（状态 ≠ 标签）必须在式样层一次定清，否则返工成本是全局的**；S1 恰是「调查确认 → 式样变更」的雏形，为起票制的调查票 / 式样变更票提供了真实案例。

### 3.3 文档与代码漂移（三例）
1. 教程第 3 页 strings 仍写「后续…打包」→ P6 收口（08-31-文档整理发现，09-01-P6 修）；
2. 画面文档残留过时 R1 措辞（08-31-文档整理）；
3. S1 本身：式样书旧条款与代码长期并存才导致状态标签蔓延。
- 规律：**漂移多发生在「文案 / 条款」类低显性内容**，靠定期全量对照（08-31-文档整理）与收口票（P6 / S1）补位。

### 3.4 prompts 填写区占位残留
- `shared/prompts/文档整理.md` 规则 6 显式要求「整理结束后**清空**『本次整理』填写区」——恰好反证这是被规则专门防范的易犯坑（模板常驻空填写区，忘清空会污染下次会话；本次建制前 `功能开发.md` 填写区即残留过 backlog 表格，已清理并改为固定空字段格式）。

### 3.5 版本号三套口径，无统一矩阵
- 事实：式样书自身文档号 v0.9；§3.1 矩阵只列依赖与 SDK，**不含 App 的 versionName / versionCode**；App 版号自建仓（08-25）后从未演进，17 篇日志零记录。
- 后果：文档版本（v0.9）、App 版本（0.0.1/曾 0.1.0）、versionCode（1）三套号互不参照，App 发版语义无权威出处。
- 本次建制已把 App 版号收敛为 0.0.1，但「统一版本矩阵（文档号 ↔ App 版本 ↔ versionCode）」仍未建——**列为下阶段候选调查票**。

### 3.6 其它小坑
- 08-25：emoji2 压制无效、Gradle 下载超时（镜像版本不全）、AGP 9.3.2 超 AS 上限降 9.2.1 → 结论「AGP 不是越新越好」。
- 08-27 日志自注「后续以 08-28 为准」：早期单日记录被后续覆盖，属早期写法冗余。
- 08-30 → 08-31：C6 重命名模板拆到 C9、C8 fromSettings 分支跨日补全——编号跨日志延续本身没问题，但当日标题省略编号（08-30 标题无 C4、08-31 主日志标题无 C3）会降低检索性。
- 短日志信息量低：08-28 仅约 9 行、多篇 08-31/09-01 为「完成项 + 关联」格式，阶段细节主要靠 08-25、08-27、08-31-文档整理、09-02-S1 四篇撑起。

## 4. 阶段一给起票制留下了什么

### 4.1 可直接承接的资产
- 编号体系延续：Bug1 / S1 已归档，新票从 **Bug2 / S2** 起；C/P 语义并入**功能 / 体验票（F）**；「待定」调研归**调查票（T）**——四类票与历史编号一一对应，见 [`票/README.md`](票/README.md)。
- 状态符号沿用：☐ 待实施 / 🚧 进行中 / ✅ 已完成 / ❌ 不采纳。
- 模板方法论复用：`_模板` 派生 + 一目录一票 + §开发记录，沿用画面文档的组织经验。
- 日志纪律升级：日志文件名带票号（原带功能号）。

### 4.2 需要补位的缺口（建议以票跟进）
1. **统一版本矩阵**（文档号 / App versionName / versionCode）→ 调查票或式样变更票；
2. **系统栏 inset / edge-to-edge 适配进画面规格**（Bug1 教训，防同类画面再犯）→ 可并入画面 _模板 或式样书统一节；
3. **概念模型先行**（如状态 ≠ 标签类）在式样层定清的流程 → 调查票前置；
4. prompts 用完清空习惯与票号贯穿 commit 的检查 → 规则已写入，靠执行养成。

### 4.3 阶段一分界（2026-09-02 建制完成）
- 目录：Android 工程下沉 `android/`，仓库根为「文档 + AI 配置」层（本轮已落地并全量刷新引用）。
- 流程：`docs/工程/票/` 起票制骨架 + 四类模板 + 分区台账就位（本轮已落地，票内容由用户陆续起）。
- 规则：dev-convention 三处同步为「起票 → 接票」版；prompts 功能开发改「本次接票」填写区。
